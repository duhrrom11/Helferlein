# Automatisch erstellter Entwicklungsvorschlag

> **Ungeprüfter KI-Entwurf.** Keine Codeänderung, kein Testlauf, kein Produktivzugriff.

Ziel
- Ergänzung eines einfachen, risikoarmen Sanitizer-Mechanismus im Nachtkoordinator-Skript (scripts/night-coordinator.cjs), bevor Zustand/Status in das öffentliche GitHub-Issue geschrieben wird. Ziel ist, versehentliche Speicherung sensibler Felder (z. B. secrets, tokens, passwortähnliche Felder oder private Chat-Inhalte) zuverlässig zu verhindern.

Betroffene Dateien
- scripts/night-coordinator.cjs

Änderungsskizze
- Ergänze in scripts/night-coordinator.cjs eine Funktion sanitizeState(state: object): object, die eine tiefe Kopie von state zurückgibt und dabei:
  - alle Eigenschaften entfernt, deren Schlüssel (case-insensitiv) mit einem der folgenden Muster übereinstimmen:
    - enthält: "secret", "token", "password", "passwd", "pw", "credentials", "auth", "access_key", "private", "vault", "treasure" (Liste anpassbar, siehe Kommentar)
  - alle String-Werte, die ein plausibles Base64-/JWT-/SSH-/RSA-Muster oder URLs mit "://secret" oder "://token" enthalten, werden ersetzt durch den String "[REDACTED-SENSITIVE]".
  - Arrays und verschachtelte Objekte werden rekursiv verarbeitet.
  - Annotation: Funktion ist rein lokal, keine Netzwerkaufrufe, keine Verwendung von Secrets.
- Vor jedem Schreiben oder Aktualisieren des Issues (also überall dort, wo currentState oder reportPayload an GitHub gesendet wird) wird sanitizeState(...) aufgerufen; gespeichert und ins Issue geschriebene JSON verwendet nur noch die bereinigte Ausgabe.
- Füge einen kleinen Testsatz inline im Code oder als Kommentar-Beispiel (nicht ausführen) hinzu, der typische Felder zeigt und das erwartete Ergebnis dokumentiert.
- Ergänze minimale JSDoc-Kommentare und einen dezenten Log-Hinweis (z. B. console.info("State sanitized: removed X sensitive fields")) — keine sensiblen Inhalte loggen.

Testplan
- Lokale Unit-Test-Ideen (keine Ausführung im Produktiv-Repo):
  1. Übergabe eines flachen Objekts mit keys { "sessionToken": "abc", "user": "alice" } -> "sessionToken" muss entfernt oder durch "[REDACTED-SENSITIVE]" ersetzt werden.
  2. Verschachteltes Objekt: { meta: { password: "pw" }, items: [{ secretKey: "x" }] } -> alle sensitiven Felder entfernt.
  3. Strings mit möglichen Token-Formaten: { note: "eyJhbGciOiJI..." } (JWT-typisches Base64-Header) -> note ersetzt durch "[REDACTED-SENSITIVE]".
  4. Unkritische Felder bleiben erhalten: { day: "2026-11-08", checks: 12 } -> diese Felder bleiben unverändert.
  5. Performance-Sanity: größeres (aber begrenztes) State-Objekt mit ~1000 Einträgen durchlaufen und prüfen, dass Laufzeit akzeptabel ist (linear).
- Manuelle Verifikation nach Änderung:
  - Führe workflow_dispatch manuell aus (wie in docs vorgeschlagen), prüfe im erzeugten Issue den JSON-Abschnitt: keine sensiblen Schlüssel oder Inhalte sichtbar.
  - Ausgaben der neuen Console-Info prüfen (z. B. Anzahl entfernter Felder).

Risiken
- Falsch negative Erkennung: sehr ungewöhnliche Sensitivitätsnamen könnten übersehen werden. (Minimales Restrisiko; Schlüsselwortliste ist konservativ gehalten.)
- Falsch positive Erkennung: nicht-sensible Felder mit Wörtern wie "privateNotes" werden entfernt und könnten nützliche Informationen vermissen lassen. (Low risk — Funktion kann bei Bedarf angepasst.)
- Performance-Overhead bei sehr großen Zuständen; der Sanitizer ist rekursiv, aber für die erwarteten Nachtbetrieb-Statusobjekte (klein bis mittel) sollte das vernachlässigbar sein.
- Diese Änderung schützt nur vor versehentlichem Schreiben sensibler Inhalte in das Issue durch den Nachtkoordinator. Andere Skripte oder Konfigurationsstellen müssen separat geprüft.
